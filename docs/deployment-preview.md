# Preview environment (preview.dupli1.com)

One shared preview of the whole shop, on VENUS next to production:

| Host | App |
|---|---|
| `https://preview.dupli1.com` | storefront (dupli1-web), with `/api/*` and `/product-images/*` |
| `https://manage-preview.dupli1.com` | admin console (dupli1-manage-web) |

A pull request whose branch starts with **`preview/`** deploys to it, from any
of the three repos, on every push. The preview runs each app at what was last
deployed for it, so a `preview/` PR in dupli1-web runs against the backend's
`main` unless a backend `preview/` PR is up too. The latest push wins: there is
one preview, not one per PR. Closing or merging the PR puts that app back on
`main` (backend) or `master` (web apps), unless a newer `preview/` PR of the same
repo has deployed since.

`manage-preview` rather than `manage.preview`: Cloudflare's free Universal SSL
certificate covers one level of subdomain (`*.dupli1.com`), not
`*.preview.dupli1.com`.

## How it is built

- **Its own stack.** `docker-compose.yml` again, under compose project
  `dupli1-preview`, with `docker-compose.preview.yml` layered on top. Own
  Postgres, Redis, NATS and SeaweedFS volumes; its own secrets in
  `/opt/dupli1-preview/.env` (generated by `preview.sh setup`); its own deploy
  checkout in `/opt/dupli1-preview/repo` and its own deploy lock. Nothing in it
  reads `/opt/dupli1`, and production's data is never copied in: the preview
  starts with an empty catalog and one owner account.
- **Same deploy script.** `preview.sh deploy` runs `deploy.sh` with the preview's
  project, env file, checkout and edge, so a preview that doesn't come up
  healthy rolls back like production does.
- **Its own edge, production's tunnel.** `preview-edge` (`nginx-edge.preview.conf`)
  routes the two preview hosts. It also joins production's `dupli1_default`
  network, where production's `cloudflared` reaches it as `preview-edge:8080`.
  Because it sits on both networks it names upstreams by container
  (`dupli1-preview-web-1`, …): a service name such as `web` would also resolve
  to production's container. Production's own `edge` is behind a profile in the
  preview, because a second container called `edge` on that network would take
  part of production's traffic. `:80` is published on `127.0.0.1:8090` only, for
  health checks.
- **No live money or bots.** Nano Pay and Telegram are empty: card checkout is
  unavailable, so pay with Bypass (as the owner, or a manager with
  `payment.bypass`); neither bot runs; no support email goes out. Put the Nano
  **test** credentials (`NANO_*`, from `.env.example`) into the preview `.env` to
  try card checkout. Every response carries `X-Robots-Tag: noindex`.
- **CI.** Each repo's `images.yml` builds a same-repo `preview/*` PR's head as
  `ghcr.io/elug3/<image>:preview-<short sha>` and runs a `preview` job on the
  VENUS runner (GitHub environment `preview`). A fork's PR never reaches the
  runner. Closing the PR runs `preview-reset`.

## One-time setup

1. **Turn it on (on VENUS)**, after this change is on `main`:

   ```bash
   cd /opt/dupli1/repo && git fetch -q origin main && git show origin/main:deploy/venus/preview.sh > /tmp/preview.sh
   OWNER_EMAIL=<your email> bash /tmp/preview.sh setup
   ```

   It writes `/opt/dupli1-preview/.env` and a fresh JWT key, clones the deploy
   checkout, pulls `main` / `master` images and starts the stack. It prints the
   owner email; the password is `OWNER_PASSWORD` in that `.env`. Check it with
   `curl -H 'Host: preview.dupli1.com' http://127.0.0.1:8090/gateway/health`.
2. **Publish the hosts (Cloudflare dashboard).** Zero Trust → Networks → Tunnels
   → the production tunnel → *Published application routes* → add
   `preview.dupli1.com` → `http://preview-edge:8080` and
   `manage-preview.dupli1.com` → `http://preview-edge:8080`. This creates the
   two DNS records; it does not touch `dupli1.com` or `manage.dupli1.com`.
3. **Put it behind Cloudflare Access (recommended).** Zero Trust → Access →
   Applications → Self-hosted, both hosts, allow your own email. The preview is
   otherwise public and runs unreviewed branch code.
4. **GitHub environment.** In each of the three repos, Settings → Environments →
   `preview` is created by the first run. Add required reviewers there if a
   preview deploy should wait for approval.

## Day to day

```bash
# what the preview runs
grep _TAG= /opt/dupli1-preview/.env; cat /opt/dupli1-preview/*.pr
# logs
docker compose -p dupli1-preview logs -f web
# put an app back by hand
/opt/dupli1-preview/repo/deploy/venus/preview.sh reset web --pr "$(cat /opt/dupli1-preview/web.pr)"
# wipe the preview's data (catalog, orders, accounts) and start over
docker compose -p dupli1-preview -f /opt/dupli1-preview/repo/deploy/venus/docker-compose.yml \
  -f /opt/dupli1-preview/repo/deploy/venus/docker-compose.preview.yml \
  --env-file /opt/dupli1-preview/.env down -v
/opt/dupli1-preview/repo/deploy/venus/preview.sh setup
```

Preview images pile up on VENUS's disk; `docker image prune -a --filter
"until=168h"` now and then clears old ones (it never removes an image a running
container uses).

## Turning it off

`docker compose -p dupli1-preview … down` (as above, add `-v` to drop its data),
remove the two published routes in the tunnel, and delete `/opt/dupli1-preview`.
`preview/` PRs then fail their `preview` job and nothing else.
